Research Report: technical

Date: 2026-03-12 Author: Teddy Research Type: technical

Research Overview​

This report presents comprehensive technical research on Chrome Extension AI Assistant architecture and technical trends, conducted as of March 2026. The research addresses nine specific technical goals covering Chrome Extension platform architecture (Manifest V3), streaming LLM response handling, enterprise SSO patterns, proxy gateway design for AI requests, hybrid model routing by data sensitivity, input sanitization and prompt injection defense, UI patterns for AI sidebars, audit logging, and the 2025–2026 technology stack landscape.

The research was conducted via systematic web research against authoritative primary sources — primarily the Chrome Developer documentation (developer.chrome.com), OWASP GenAI Security Project, and Chrome Extension API reference. All claims are verified against live sources; uncertain claims are marked with confidence levels. The research produced findings across five analytical dimensions: Technology Stack Analysis, Integration Patterns, Architectural Patterns, Implementation Approaches, and Strategic Recommendations.

Key findings establish that Genie's proposed architecture is well-aligned with current best practices: the chrome.sidePanel API (Chrome 114+, MV3) is the standard for persistent AI sidebars; chrome.runtime.connect() long-lived ports are the correct mechanism for streaming; chrome.identity.launchWebAuthFlow() supports non-Google enterprise SSO; and genie-api's role as an authenticated proxy gateway with hybrid model routing directly addresses OWASP LLM Top 10 threats. See the Executive Summary below for the complete synthesis and strategic recommendations.

Technology Stack Analysis​

Programming Languages​

Chrome extensions in 2025–2026 are written primarily in TypeScript and JavaScript. TypeScript has become the dominant choice for enterprise-grade extensions due to static typing, better IDE support, and maintainability at scale. JavaScript (ES2022+) remains viable for smaller extensions.

Popular Languages:

  • TypeScript — dominant for enterprise Chrome extensions; used in most production AI assistant extensions for type safety and maintainability
  • JavaScript (ES2022+) — still used, especially in simpler extensions or alongside TypeScript
  • HTML/CSS — for side panel UI and popup pages

Emerging Languages: WebAssembly (WASM) is gaining traction for performance-critical operations (e.g., running on-device ML inference within extensions), but remains niche for general extension development.

Language Evolution: MV3 migration (2023–2025) pushed the ecosystem toward ES modules and modern async/await patterns. "type": "module" is now supported in service workers.

Performance Characteristics: TypeScript compiles to standard JS — no runtime overhead. Key bottleneck is service worker lifecycle (MV3 service workers are ephemeral and can be terminated by Chrome).

Source: https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/basics

Development Frameworks and Libraries​

UI Layer — Side Panel:

  • React — most popular UI framework for extension side panels and popup pages; ecosystem maturity, component model well-suited to chat/sidebar UIs
  • Preact — lightweight React alternative (3KB); preferred when bundle size matters
  • Svelte / SvelteKit — gaining adoption for extensions due to zero-runtime compiled output; ideal for side panel performance
  • Vanilla JS + Web Components — used in Google's own extension samples for simplicity and no framework overhead

Build Tooling:

  • Vite + vite-plugin-web-extension — dominant build setup for modern Chrome extensions in 2025; fast HMR, TypeScript support, multi-entry (service worker + content scripts + side panel)
  • Webpack — older standard, still used in many enterprise extensions; heavier configuration
  • esbuild — used under the hood by Vite; also used directly for lightweight extension builds
  • CRXJS (Vite plugin) — enables HMR in extension pages during development

State Management:

  • Zustand — lightweight; popular for side panel state in React-based extensions
  • Jotai / Nanostores — atomic state management; avoids Redux complexity
  • chrome.storage.local / chrome.storage.session — native Chrome storage APIs used as the persistence layer; synced state between service worker and side panel via chrome.storage.onChanged

Major Frameworks: React (most common), Svelte (growing), Preact (bundle-conscious) Evolution Trends: Move away from Webpack toward Vite; increasing use of TypeScript as baseline Ecosystem Maturity: Extension-specific libraries remain sparse; most teams adapt generic web frameworks

Source: https://developer.chrome.com/docs/extensions/reference/api/sidePanel

Message Passing for Streaming Responses​

Long-lived connections (chrome.runtime.connect()) are the correct mechanism for streaming LLM responses in MV3 extensions:

// Side panel establishes long-lived connection to service worker
const port = chrome.runtime.connect({ name: "llm-stream" });

// Service worker receives SSE/fetch stream from genie-api,
// forwards chunks to side panel via port
port.onMessage.addListener((msg) => {
  if (msg.type === 'chunk') renderChunk(msg.data);
  if (msg.type === 'done') finalizeResponse();
});

port.postMessage({ type: 'start', prompt: userInput });

Key constraints:

  • chrome.runtime.sendMessage() is one-time only — not suitable for streaming
  • chrome.runtime.connect() creates a persistent port — correct for streaming
  • Max message size: 64 MiB
  • Content scripts are less trusted than service workers — always validate/sanitize messages from content scripts
  • Do NOT use innerHTML with data from content scripts (XSS risk); use innerText or DOM APIs

Source: https://developer.chrome.com/docs/extensions/develop/concepts/messaging

Integration Patterns Analysis​

API Design Patterns​

Extension ↔ genie-api Communication:

The primary integration pattern for Genie is REST + SSE (Server-Sent Events) over HTTPS:

  • REST for stateless requests: auth token validation, non-streaming queries, configuration fetch
  • SSE for streaming LLM responses: genie-api streams token chunks back to the extension service worker, which forwards them to the side panel via long-lived port connections

Why not WebSockets? SSE is simpler and sufficient for unidirectional server→client streaming (LLM output). WebSockets are bidirectional — unnecessary overhead for LLM response delivery. SSE also works natively with the fetch() API using ReadableStream.

// Service worker: fetch SSE stream from genie-api
const response = await fetch('https://local-api.genie.local/chat', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${authToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ prompt, context, sessionId })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

// Forward chunks to side panel via long-lived port
while (true) {
  const { done, value } = await reader.read();
  if (done) { port.postMessage({ type: 'done' }); break; }
  const chunk = decoder.decode(value);
  port.postMessage({ type: 'chunk', data: chunk });
}

Source: https://developer.chrome.com/docs/ai/streaming

Communication Protocols and Data Formats​

HTTP/HTTPS (Mandatory):

  • All cross-origin requests from extension service workers use fetch() with HTTPS
  • XMLHttpRequest is deprecated in service workers; use fetch() exclusively
  • Extension must declare host_permissions in manifest for the genie-api origin: 
    "host_permissions": ["https://local-api.genie.local/*"]

SSE (Server-Sent Events) — LLM Streaming:

  • Standard format: each event is a data: line followed by newline
  • Compatible with ReadableStream consumption in the service worker
  • Server sends data: [DONE] or similar sentinel to signal stream end
  • Reconnection handled automatically by the browser SSE spec

JSON — Standard Data Exchange:

  • All extension ↔ genie-api request/response bodies use JSON
  • chrome.runtime message passing uses JSON serialization (Chrome-specific — not structured clone like Firefox)
  • Message size limit: 64 MiB per message

Security constraint: Prefer HTTPS always. HTTP requests on hostile networks are subject to MITM attacks. MV3 CSP defaults block mixed content.

Source: https://developer.chrome.com/docs/extensions/develop/concepts/network-requests

SSO/Authentication Integration Pattern​

chrome.identity.launchWebAuthFlow() — Enterprise SSO:

For non-Google identity providers (e.g., CyberAgent's internal SSO/SAML), launchWebAuthFlow is the correct API:

// In service worker
const redirectUrl = chrome.identity.getRedirectURL();
// → "https://<extension-id>.chromiumapp.org/"

const authUrl = `https://sso.cyberagent.co.jp/oauth/authorize?` +
  `client_id=genie-extension&` +
  `redirect_uri=${encodeURIComponent(redirectUrl)}&` +
  `response_type=code&scope=openid profile email`;

const responseUrl = await chrome.identity.launchWebAuthFlow({
  url: authUrl,
  interactive: true
});

// Parse authorization code from responseUrl
// Exchange for access token via genie-api /auth/token endpoint

Token storage and management:

  • Store access tokens in chrome.storage.session (cleared when browser closes; not persisted to disk)
  • Refresh tokens optionally in chrome.storage.local (encrypted by Chrome)
  • Never store tokens in chrome.storage.sync (synced to cloud — security risk)
  • chrome.identity.removeCachedAuthToken() for token invalidation

Token forwarding to genie-api:

  • Extension service worker attaches Authorization: Bearer <token> header to all genie-api requests
  • genie-api validates token with SSO provider, enforces employee-only access
  • Token refresh handled transparently: on 401 response, re-run launchWebAuthFlow and retry

Source: https://developer.chrome.com/docs/extensions/reference/api/identity

API Gateway Pattern (genie-api as LLM Proxy)​

Role of genie-api in the integration:

genie-api acts as a secure API gateway between the Chrome extension and external/internal AI models:

Chrome Extension
     ↓ (HTTPS + Bearer token)
genie-api (Node.js/Docker)
     ├── Auth middleware (SSO token validation)
     ├── Input sanitization layer
     ├── Model router (internal vs. external LLM)
     ├── Rate limiter
     ├── Audit logger
     └── Response streamer (SSE back to extension)
          ↓                    ↓
   CyberAgent Internal     External LLM API
   LLM (sensitive data)    (non-sensitive data)

Gateway responsibilities:

  1. Authentication — Validate SSO tokens before any LLM call
  2. Input sanitization — Strip/escape prompt injection attempts before forwarding to LLM
  3. Model routing — Classify request sensitivity, route to internal or external model
  4. Rate limiting — Prevent abuse; per-user token budget enforcement
  5. Audit logging — Log all requests with user ID, prompt hash, model used, timestamp
  6. Response streaming — Forward LLM SSE stream to extension client
  7. Content filtering — Optionally post-process LLM output before delivery

CORS configuration:

  • genie-api must allow the extension origin (chrome-extension://<extension-id>)
  • Configure Access-Control-Allow-Origin accordingly in genie-api Express/NestJS middleware

Source: https://developer.chrome.com/docs/extensions/develop/concepts/network-requests

Content Script → Service Worker Integration​

Security-critical pattern: Content scripts run in the context of web pages and are less trusted. The correct integration pattern limits what content scripts can request:

// SECURE: Content script sends only sanitized, typed data
// content-script.js
chrome.runtime.sendMessage({
  type: 'SUMMARIZE_PAGE',
  payload: {
    selectedText: document.getSelection().toString().slice(0, 5000), // limit length
    pageUrl: window.location.href,
    pageTitle: document.title
  }
});

// INSECURE (never do this): content script controls the URL fetched
// chrome.runtime.sendMessage({ type: 'FETCH_URL', url: arbitraryUrl });

Service worker validates all content script messages:

// service-worker.js
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (!sender.tab) return; // reject non-tab senders
  if (msg.type !== 'SUMMARIZE_PAGE') return;

  // Validate and sanitize payload before sending to genie-api
  const sanitized = sanitizePayload(msg.payload);
  callGenieApi(sanitized).then(sendResponse);
  return true; // async response
});

Source: https://developer.chrome.com/docs/extensions/develop/concepts/messaging

Integration Security Patterns​

OAuth 2.0 / SSO:

  • chrome.identity.launchWebAuthFlow() for non-Google SSO providers
  • Short-lived access tokens (1 hour) stored in chrome.storage.session
  • PKCE (Proof Key for Code Exchange) recommended for OAuth2 flows

Cross-origin Request Security:

  • Extension service worker has host_permissions for genie-api only
  • Content scripts cannot make direct cross-origin requests to genie-api
  • All AI requests flow through service worker (trusted context)
  • content_security_policy in manifest restricts script sources

Input Sanitization (XSS prevention):

  • Content from web pages treated as untrusted HTML
  • Use element.textContent or document.getSelection().toString() (plain text) — never innerHTML
  • Limit selected text length before forwarding (prevent token stuffing attacks)
  • genie-api performs second-layer sanitization before LLM submission

Mutual TLS / HTTPS:

  • All extension ↔ genie-api communication over HTTPS (TLS 1.3)
  • For local development: localhost or local-api.genie.local with self-signed cert
  • Production: valid TLS certificate on genie-api domain

Architectural Patterns and Design​

System Architecture Patterns​

Architectural Pattern: Hub-and-Spoke with Trusted Core

The service worker acts as the trusted hub. All sensitive operations (auth token management, LLM API calls, audit logging) are centralized in the service worker. Content scripts and the side panel are spokes that communicate only through typed, validated messages.

Dominant Patterns: Event-driven, hub-and-spoke, trust boundary separation Architectural Trade-offs: Complexity of multi-context coordination vs. security isolation benefits

Source: https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts

Design Principles and Best Practices​

Principle of Least Privilege (MV3 native):

MV3 enforces minimal permissions by design:

  • Extensions declare only the APIs and host_permissions they need
  • "activeTab" permission grants temporary access to current tab without broad host permissions
  • Content scripts run in isolated worlds — cannot access extension APIs beyond a limited subset
  • Service workers cannot run persistent code; must be event-driven

Chrome Security Model (Trust Hierarchy):

ContextTrust LevelCapabilitiesRisk
Service WorkerHighAll Chrome APIs, network fetchEphemeral termination
Side PanelHighAll Chrome APIs, full DOMLong-running UI context
Content ScriptMediumLimited APIs, web page DOMRenderer compromise possible
Web PageUntrustedNo extension APIsHostile page attacks

Key design rule from Google: "Operations using sensitive data or Chrome APIs with access to the browser's functions should be performed in the extension's service worker. Avoid accidentally exposing extension privileges to content scripts."

Input Sanitization Architecture:

Google explicitly documents these as dangerous patterns (forbidden in MV3):

// FORBIDDEN: eval with untrusted input
const parsed = eval("(" + data + ")");

// FORBIDDEN: setTimeout with string argument
window.setTimeout("animate(" + elmt_id + ")", 200);

// SAFE: JSON.parse instead of eval
const parsed = JSON.parse(data);

// SAFE: Closure form of setTimeout
window.setTimeout(() => animate(elmt_id), 200);

innerHTML with user data must be replaced by innerText or DOM node creation:

// SAFE: Create DOM nodes, use innerText
function constructDOM() {
  let newTitle = document.createElement('h1');
  newTitle.innerText = host; // sanitized text, not raw HTML
  document.appendChild(newTitle);
}

Design Principles: Least privilege, trust boundary enforcement, input sanitization at each layer Best Practice Patterns: Hub-and-spoke service worker, DOM API over innerHTML, CSP default-src 'self'

Source: https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure

Scalability and Performance Patterns​

Service Worker Lifecycle Management (Critical for Streaming):

MV3 service workers are ephemeral — Chrome can terminate them when idle. This creates a critical architectural challenge for streaming LLM responses:

  • Problem: If service worker is terminated mid-stream, the SSE connection to genie-api drops
  • Solution pattern: Use long-lived ports (chrome.runtime.connect()) to keep service worker alive during active streaming; the side panel's open port prevents termination
  • Keepalive pattern: Periodic chrome.storage writes or chrome API calls can extend service worker lifetime during long operations

Side Panel Performance Architecture:

For AI chat UIs with streaming responses:

  • Incremental rendering: Render streamed text chunks immediately as they arrive — do not buffer until complete
  • Markdown parsing challenge: Streamed chunks can split in the middle of markdown syntax (e.g., **bo in one chunk, ld** in the next). Solution: use an incremental markdown parser (e.g., marked with streaming mode, or custom state machine)
  • Virtual DOM efficiency: React/Preact's diffing handles incremental updates efficiently; avoid full re-renders on each chunk
  • Message list pagination: For long chat sessions, virtualize the message list (react-virtual or similar) to avoid DOM bloat

State Management Architecture:

Side Panel State (React/Zustand)        Persisted State (chrome.storage)
┌────────────────────────────┐          ┌─────────────────────────────┐
│ - currentStreamedText       │◄────────►│ - chatHistory (local)       │
│ - isStreaming               │          │ - authToken (session)        │
│ - messages[]                │          │ - userPreferences (local)    │
│ - selectedMode              │          │ - sessionId (session)        │
└────────────────────────────┘          └─────────────────────────────┘
         ▲                                          ▲
         │ chrome.storage.onChanged                 │
         └──────────────── Service Worker ──────────┘

Scalability Patterns: Ephemeral SW keepalive via ports, incremental rendering, storage-based state sync Performance Optimization: Incremental markdown parsing, virtual DOM for streaming, message list virtualization

Source: https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/basics

Integration and Communication Patterns​

Message Flow Architecture (Three-Layer):

Layer 1: Web Page → Content Script
  - DOM events (text selection via chrome.contextMenus)
  - window.postMessage if web page initiates

Layer 2: Content Script → Service Worker
  - chrome.runtime.sendMessage() (one-time, small payloads)
  - chrome.runtime.connect() (long-lived for streaming)
  - Messages: sanitized, typed, size-limited

Layer 3: Service Worker → genie-api
  - fetch() with HTTPS + Bearer token
  - SSE streaming response (ReadableStream)
  - Response forwarded to Side Panel via port

Security Architecture Patterns​

Defense in Depth: Four Layers

Genie's architecture implements defense at every layer:

Layer 1 — Browser/MV3 Enforcement:

  • CSP default-src 'self' prevents remote code injection
  • No eval() or remote-hosted scripts allowed
  • host_permissions limits which origins can be fetched
  • Isolated worlds prevent content script ↔ web page JavaScript access

Layer 2 — Content Script Boundary:

  • Content scripts treated as less-trusted despite being extension code
  • chrome.runtime messages from content scripts validated in service worker
  • Renderer process compromise (Spectre-style) is a known risk — sensitive data never sent to content scripts
  • Sensitive operations (API calls, token handling) done in service worker only

Layer 3 — Service Worker Validation:

  • All incoming messages validated: sender identity, message type, payload schema
  • Content scripts cannot trigger arbitrary URLs or pass unconstrained arguments
  • Token stored in chrome.storage.session (session-only, not disk-persisted)

Layer 4 — genie-api Gateway:

  • SSO token validated server-side before any LLM call
  • Second-layer input sanitization at API gateway
  • Rate limiting per user
  • Audit log for compliance (user ID, prompt hash, model used, timestamp)

Technology Adoption Strategies​

MV3 Adoption (2023–2025):

The Chrome Extensions ecosystem completed a major platform migration from Manifest V2 to Manifest V3. Key adoption lessons relevant to Genie:

  • Incremental migration pattern: Teams that migrated MV2 extensions to MV3 incrementally (service worker first, then CSP, then network request handling) had fewer regressions than big-bang rewrites
  • Blocking web requests → declarativeNetRequest: MV3 removed chrome.webRequest blocking. Genie does not need ad-blocking, so this is not a concern
  • Background pages → Service Workers: The most disruptive MV3 change. Ephemeral service workers require a fundamentally different approach to state persistence (use chrome.storage, not in-memory globals)
  • Remote code → bundled code: MV3 prohibits all remote code execution. This enforces good practice: all extension logic must be shipped in the .crx package

Executive Summary​

Browser-based enterprise AI assistants are a mature and actively evolving product category in 2025–2026, with Chrome Manifest V3 providing a stable, security-hardened platform for their development. This research confirms that Genie's proposed architecture — a Chrome extension with sidebar injection, SSE streaming, SSO authentication, and an internal API proxy (genie-api) — is not only technically feasible but represents current best practice for enterprise AI assistant deployment.

The research identified five critical architectural decisions that define the success of any Chrome Extension AI assistant:

  1. Side Panel over iframe injection — chrome.sidePanel (Chrome 114+, MV3) is the official, stable API for persistent AI sidebars. It provides full access to Chrome APIs, persists across tab navigation, and eliminates the complexity and security risks of manual iframe injection.

  2. Service Worker as trusted hub — The MV3 trust model mandates that all sensitive operations (authentication, LLM API calls, token management) reside in the service worker. Content scripts are less trusted and run in the renderer process; they must not handle tokens or make direct API calls.

  3. Long-lived ports for streaming — chrome.runtime.connect() is the correct mechanism for streaming LLM responses. sendMessage() is one-shot only. The open port also prevents premature service worker termination — a critical design consideration given MV3's ephemeral service worker lifecycle.

  4. genie-api as security boundary — Routing all AI requests through an internal proxy eliminates direct extension-to-LLM API communication, centralizes authentication enforcement, enables hybrid model routing by data sensitivity, and provides audit trail capability for compliance. This pattern directly mitigates five of the OWASP LLM Top 10 threats.

  5. Defense in depth at four layers — MV3/CSP enforcement, content script validation, service worker message sanitization, and genie-api gateway sanitization together provide robust protection against prompt injection (OWASP LLM01), insecure output handling (LLM02), and data leakage (LLM06).

Key Technical Findings:

  • chrome.sidePanel API is stable since Chrome 114 (2023); open() available Chrome 116+; onOpened/onClosed events Chrome 141+/142+
  • Service workers are ephemeral in MV3 — must not use in-memory state; all persistence through chrome.storage
  • chrome.identity.launchWebAuthFlow() supports SAML/OAuth2 SSO for non-Google identity providers; tokens stored in chrome.storage.session (session-only, not disk-persisted)
  • SSE over HTTPS is the standard pattern for LLM streaming; consumed via ReadableStream fetch in service worker, forwarded to side panel via port
  • Incremental markdown rendering requires special handling (chunks can split mid-syntax)
  • OWASP LLM Top 10 (2025): Prompt Injection (LLM01) is the #1 threat; mitigated by two-layer sanitization (content script boundary + genie-api)
  • Recommended tech stack: TypeScript 5 + React 19 + Vite 6 + Vitest + Playwright

Technical Recommendations:

  1. Use chrome.sidePanel as the only UI surface — Do not attempt manual sidebar injection via content scripts
  2. Store all auth tokens in chrome.storage.session — Never chrome.storage.sync (cloud-synced = security risk)
  3. Implement two-layer input sanitization — Content script (text extraction, length limit) + genie-api (prompt sanitization before LLM submission)
  4. Use phased implementation roadmap — Foundation → Streaming → Content Integration → Production Hardening (16 weeks)
  5. Log prompt hashes, not raw prompts — SHA-256 hash for audit trail; raw prompt retention requires legal review for PII compliance

2. Key Technical Insights (Cross-Cutting)​

The MV3 Trust Model Is Foundational​

Everything in Chrome extension security flows from one principle: content scripts run in the renderer process of the web page and must be treated as less trusted. This is not just a Google recommendation — it reflects a real attack vector. A compromised web page can potentially manipulate content script behavior through the shared DOM, and Spectre-class side-channel attacks can leak content script memory to the hosting page.

The correct response is to ensure that:

  • Sensitive data (auth tokens, user PII, API keys) never reaches content scripts
  • Content scripts send only sanitized, typed, size-limited messages to the service worker
  • The service worker validates the identity and schema of all incoming messages
  • All privileged Chrome API calls originate from the service worker or side panel

This trust model maps directly to Genie's architecture: content scripts extract page text and capture selection events, but all AI requests are made from the service worker via genie-api.

Streaming Architecture Is the Critical Path​

The streaming pipeline is the highest-complexity component of the entire system:

User Input (Side Panel)
  → chrome.runtime.connect() port → Service Worker
    → fetch(genie-api/chat, SSE) → genie-api
      → [Model Router] → LLM (internal or external)
        → SSE chunks → genie-api → Service Worker
          → port.postMessage(chunk) → Side Panel
            → Incremental render → User sees streaming text

Each arrow is an async handoff with its own error mode. The key implementation challenges are:

  1. Service worker termination during streaming (mitigated by long-lived port keepalive)
  2. Markdown chunk splitting (mitigated by incremental parser state machine)
  3. SSE reconnection on network interruption (handled by genie-api reconnect logic)
  4. Port disconnection on side panel close (gracefully terminate stream in service worker)

Enterprise Deployment Requires Platform-Specific Knowledge​

Chrome Enterprise deployment is a distinct skill set from standard web deployment:

  • Force-install via ExtensionInstallForcelist group policy (Windows GPO / macOS MDM)
  • Fixed extension ID requires managing the key pair from the first publish
  • Private Chrome Web Store listing (unlisted) vs. self-hosted CRX server
  • Version pinning via ExtensionInstallAllowlist + ExtensionSettings

Technical Research Conclusion​

Summary of Key Technical Findings​

  1. Architecture: Hub-and-spoke with service worker as trusted hub is the correct MV3 pattern. Side panel (chrome.sidePanel) is the stable, official API for persistent AI UI.

  2. Streaming: SSE + ReadableStream + long-lived ports (chrome.runtime.connect()) is the complete streaming pipeline. Service worker ephemeral lifecycle is the primary streaming risk — mitigated by port keepalive.

  3. Security: Two-layer input sanitization (content script + genie-api) + output rendering via innerText (not innerHTML) covers the top OWASP LLM threats applicable to browser-based AI.

  4. Authentication: chrome.identity.launchWebAuthFlow() for enterprise SSO + chrome.storage.session for token storage is the correct, secure pattern.

  5. Tech Stack: TypeScript 5 + React 19 + Vite 6 + vite-plugin-web-extension + Vitest + Playwright is the 2025–2026 consensus stack for enterprise Chrome extension development.

Strategic Technical Impact Assessment​

Genie's architecture as described is technically sound and aligns with current Chrome platform capabilities and security best practices. The primary technical risks are operational (service worker lifecycle management, SSE connection reliability) rather than architectural. The hybrid model routing pattern (internal LLM for sensitive data, external for general queries) is a differentiating feature that requires careful implementation of the data sensitivity classification layer.

The 16-week phased implementation roadmap provides a realistic path from foundation to production-ready enterprise deployment, with security hardening (audit logging, prompt injection testing, enterprise policy setup) appropriately deferred to the final phase after core functionality is validated.

Next Steps​

  1. Start with foundation phase: Set up Vite build, MV3 manifest, basic side panel UI, SSO auth
  2. Validate streaming architecture early: Implement SSE streaming in phase 2 before content integration
  3. Security review at phase 3: Conduct prompt injection testing when content script page extraction is complete
  4. Engage IT/enterprise team early: Enterprise policy deployment (phase 4) requires IT coordination — start planning in phase 2
