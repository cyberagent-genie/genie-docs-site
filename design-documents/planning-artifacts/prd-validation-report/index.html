Implementation Leakage Validation​

Leakage by Category​

Frontend Frameworks: 0 violations

Backend Frameworks: 0 violations

Databases: 0 violations

Cloud Platforms: 0 violations

Infrastructure: 0 violations

Libraries: 0 violations

Other Implementation Details: 4 violations

  • FR7: "server-side conversation history scoped to SSO session ID" — "server-side" prescribes WHERE data is stored (implementation); "SSO session ID" prescribes HOW scoping is implemented. Capability statement should read: "System maintains conversation history scoped to the user's authenticated session"
  • FR42: "genie-api auto-invalidates server-side sessions after an IT Admin-configurable idle timeout" — "server-side sessions" is implementation detail. Should read: "System auto-invalidates user sessions after an IT Admin-configurable idle timeout"
  • FR43: "genie-api enforces model allowlist server-side" — "server-side" specifies WHERE enforcement happens. Should read: "System enforces model allowlist on every AI request regardless of request source"

Note: NFR protocol references (TLS 1.2+, SAML 2.0, OIDC, REST API v2, Manifest V3) are capability-relevant compliance/integration standards — not implementation leakage.

Summary​

Total Implementation Leakage Violations: 4 (all in FRs 7, 42, 43 — same "server-side" pattern)

Severity: Warning ⚠️

Recommendation: Leakage is minor and concentrated in three FRs with the same pattern ("server-side"). Remove "server-side" and "SSO session ID" terminology from FR language — these belong in the architecture document. The intended capability (session-scoped conversation history, session invalidation, server-enforced allowlist) can be expressed without implementation location details.

Top 3 Improvements​

  1. Add Office Staff User Journey narrative Success criterion for Office Staff exists ("processes reports without external AI") but no journey narrative supports it. Adding a Journey for Hana persona (similar depth to Comtor/Developer journeys) fixes the traceability gap, gives UX/Design a concrete persona story, and validates the PRD's claim that this is a three-persona product.

  2. Specify conversation history depth (FR8) and add missing FRs for recency signal and data export Three capability gaps across User Journeys: (a) FR8 needs a bounded history depth (e.g., "last 10 turns" or "full session"); (b) Journey 3 Developer narrative references a document freshness/recency signal with no backing FR; (c) Journey 5 CTO narrative references data export with no backing FR or explicit deferral statement.

A focused pass to express these capabilities without location implementation details (e.g., "server-side" → remove; "SSO session ID" → "authenticated session") will make these FRs properly capability-focused and architecture-agnostic.
