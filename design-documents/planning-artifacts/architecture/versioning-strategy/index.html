Versioning Strategy

ADR-007: Versioning Strategy — All Layers​

Layer 1: genie-db Go Module Versioning​

v0.x.y  — pre-stable (pilot phase)
v1.x.y  — stable (post-pilot, production)
Change typeVersion bumpgenie-api action
Add nullable column / Add tableMINOR (v0.1.0 → v0.2.0)go get + optional use
Rename / Drop column / Change typeMAJOR (v0.x → v1.0)Breaking — coordinate deploy
Data migration only (no schema change)PATCH (v0.1.0 → v0.1.1)go get only

Tagging: git tag v0.2.0 && git push origin v0.2.0

Layer 2: REST API Versioning (extension ↔ genie-api contract)​

  • All routes: /api/v1/ — breaking changes → /api/v2/ (old prefix kept alive during grace period)
  • Grace period: /api/v_prev/ active for 2 sprints after breaking change (Chrome Web Store review lag)
  • ExtensionMessage.version: 1 — service worker negotiates version, sends VERSION_MISMATCH error if incompatible (PM-5)

Extension bundle semver:

  • MAJOR — breaking API contract (requires genie-api v2 + extension update)
  • MINOR — new feature, backward compatible
  • PATCH — bug fix

Layer 3: Docker Image Pinning​

All images pinned to MAJOR.MINOR.PATCH (FM-4). No latest tags. Update via explicit PR to docker-compose.yml.

Layer 4: Data Versioning​

Redis — Conversation History (versioned payload + migration-on-read)​

Each conversation turn embeds a v field. On read, if v < current → apply migration function → return normalized struct. TTL 8h ensures old format auto-expires — no migration script needed.

// v1 format (current)
{ "v": 1, "role": "user", "text": "...", "ts": "2026-03-16T09:00:00Z" }

// v2 format (example: adding action field)
{ "v": 2, "role": "user", "text": "...", "ts": "...", "action": "translate" }
// internal/infrastructure/cache/conversation_migrator.go
func migrateConversationTurn(raw json.RawMessage) (ConversationTurn, error) {
    var versioned struct{ V int `json:"v"` }
    json.Unmarshal(raw, &versioned)
    switch versioned.V {
    case 1:
        // migrate v1 → current format
    default:
        // unmarshal as current format
    }
}

MySQL — Schema Migrations (Expand/Contract pattern — mandatory for destructive changes)​

NEVER run DROP COLUMN / DROP TABLE / RENAME COLUMN directly on staging or production. All destructive schema changes MUST follow the 3-phase Expand/Contract pattern:

Phase 1 — Expand (genie-db v0.x+1):
  ADD COLUMN `action_new` VARCHAR(50) NULL
  → deploy genie-api: write to both `action` and `action_new`
  → rollback safe: old column untouched

Phase 2 — Migrate (genie-db v0.x+1, patch script):
  backfill: UPDATE audit_logs SET action_new = action WHERE action_new IS NULL
  → rollback safe: both columns have data

Phase 3 — Contract (genie-db v0.x+2):
  DROP COLUMN `action`        ← only after genie-api no longer reads it
  → rollback: data already in `action_new`, no loss

Local dev: migrate reset allowed — seed data is regenerated anyway. Staging/Production: Expand/Contract mandatory. No exceptions.

Enforce via PR checklist in genie-db:

  • Does this migration DROP or RENAME anything? → Must be Phase 3 of Expand/Contract
  • Is Phase 1 (Expand) already deployed and verified? → Required before Phase 3

Qdrant — Confluence Vector Index (versioned collections + blue-green reindex)​

Collection name driven by env var — never hardcoded:

GENIE_QDRANT_COLLECTION=genie_confluence_v1   # current

When embedding model changes (dimension change → incompatible vectors):

Step 1: Create new collection genie_confluence_v2 (new vector_size, new model)
Step 2: Run full reindex into v2 in background (v1 still serves traffic)
Step 3: Set GENIE_QDRANT_COLLECTION=genie_confluence_v2 in env
Step 4: Deploy genie-api → traffic switches to v2
Step 5: Drop genie_confluence_v1 after 1 sprint grace period

ensureCollection() in NewQdrantProvider() reads collection name from GENIE_QDRANT_COLLECTION env var — creates if not exists, skips if already exists.

Add to .env.example:

GENIE_QDRANT_COLLECTION=genie_confluence_v1
